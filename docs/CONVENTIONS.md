# 저장소 작업 규칙 (peekops)

peekops는 홈서버에서 **실제로 장애 진단에 쓰는 도구**다.
`main`은 서버에 배포되는 버전이므로, `main`에 들어간 변경은 다음 진단 주기(10분)부터 운영에 영향을 준다.
사람이든 AI든 아래 규칙을 똑같이 따른다.

---

## 1. 작업 흐름

```
문제 발견/개선 아이디어 → Issue 등록 → 브랜치 생성 → 커밋 → PR (Closes #이슈) → CI 통과 → 검토 → Squash merge → 서버 반영 → 검증 결과 댓글 → Issue 자동 종료
```

- `main`에 직접 push하지 않는다. 모든 변경은 PR을 거친다.
- PR은 **하나의 목적**만 다룬다. 서로 다른 이슈를 한 PR에 섞지 않는다.
- merge는 **Squash merge**를 사용한다. PR 제목이 그대로 `main`의 커밋 메시지가 된다.
- merge 후에는 서버에 반영하고, PR 본문의 "검증" 항목을 실제로 실행해 결과를 댓글로 남긴다.

### Issue가 필요한 경우 / 생략 가능한 경우

| 상황 | Issue |
|---|---|
| 오동작, 파싱 실패, 잘못된 알림 등 운영 중 발견한 문제 | **필수** (`bug` 템플릿) |
| 기능 추가, 구조 개선 | 권장 (`enhancement` 템플릿) |
| 명령어 실행 범위, 비밀값 등 보안 관련 | **필수** (`enhancement` 템플릿 + `security` 라벨) |
| 오타, 주석, 문서만 수정하는 작은 변경 | 생략 가능 |

운영 중 발견한 문제는 고친 뒤라도 Issue로 남긴다. 기록이 다음 판단의 근거가 된다.

## 2. 이름 규칙

### 유형(type)

| type | 용도 |
|---|---|
| `feat` | 새 기능 추가 |
| `fix` | 오동작 수정 |
| `perf` | 진단 시간, 턴 수, 리소스 사용량 개선 |
| `refactor` | 동작 변화 없는 구조 정리 |
| `chore` | 의존성, 설정값 조정 등 유지보수 |
| `security` | 명령어 실행 범위, 비밀값, 권한 관련 조치 |
| `test` | 테스트만 추가·수정 |
| `docs` | 문서만 변경 |
| `ci` | `.github/` 워크플로 변경 |
| `revert` | 이전 변경 되돌리기 |

### 범위(scope)

디렉터리 구조를 그대로 따른다.

| scope | 대상 경로 |
|---|---|
| `collector` | `collectors/**` (시스템 · Kubernetes 지표 수집) |
| `detector` | `analyzers/detector.py` (임계치 기반 이슈 감지) |
| `react` | `analyzers/react.py` (ReAct 루프, 명령어 실행) |
| `llm` | `analyzers/llm.py` (LLM 클라이언트) |
| `notifier` | `notifiers/**` (Discord 알림 · 리포트) |
| `exporter` | `exporters/**`, `aiops_exporter.py` (Prometheus) |
| `core` | `core/**`, `config.py`, `main.py`, `report.py` |
| `repo` | 저장소 전체 규칙, `docs/`, `.github/`, `tests/` 기반 |

여러 scope에 걸치면 주된 하나를 쓰고, 본문 "영향 범위"에 나머지를 적는다.

### 브랜치

```
<type>/<scope>-<짧은-설명>
```

- 영어 소문자, 단어는 `-`로 연결, 설명은 2~5단어
- Issue 번호는 브랜치에 넣지 않는다 (PR 본문에서 `Closes #n`으로 연결)

예시
```
fix/llm-strip-think-block
fix/react-kubectl-namespace
security/react-command-validation
feat/react-issue-anchors
docs/repo-conventions
```

### PR 제목 (= squash 커밋 메시지)

```
<type>(<scope>): <한글 요약>
```

- 무엇을 바꿨는지가 아니라 **무엇이 좋아지는지/해결되는지**가 드러나게 쓴다
- 50자 안팎, 마침표 없음

예시
```
fix(llm): think 블록이 섞인 응답의 파싱 실패 해결
security(react): 파이프 · 명령 연결을 통한 허용 목록 우회 차단
feat(react): 이슈별 앵커(PID · Pod)로 조사 시작점 제공
```

### 브랜치 안의 개별 커밋

```
<type>(<scope>): <영문 또는 한글 요약>
```
squash되므로 엄격하지 않아도 되지만 위 형식을 권장한다.

## 3. PR 본문

`.github/pull_request_template.md`가 자동으로 채워진다. 모든 항목을 채우고, 해당 없으면 "해당 없음"이라고 적는다.

| 섹션 | 쓸 내용 |
|---|---|
| 배경 | 왜 필요한가. 관찰한 현상과 근거(로그, 진단 출력, 재현 방법)를 함께 |
| 변경 사항 | 파일/함수 단위로 무엇을 바꿨는가 |
| 영향 범위 | 바뀌는 동작, 추가·변경된 설정과 환경변수, 서버에서 재시작이 필요한 서비스 |
| 검증 | 로컬 테스트 결과 + merge 후 서버에서 실행할 명령과 기대 결과. 서버 실행 결과는 댓글로 추가 |
| 롤백 | 문제 시 되돌리는 방법 (대부분 `git revert <squash 커밋>`) |
| 관련 | `Closes #n`, 참고 문서, 이전 PR |

### 검증 원칙

- 동작을 바꾸는 PR은 **테스트를 함께 추가**한다. `python -m pytest`가 통과해야 merge한다.
- 테스트는 실제 서버 · Ollama · Discord 없이 돌아가야 한다. LLM 응답과 명령 실행 결과는 가짜 값으로 대신한다.
- 서버에서만 확인 가능한 항목(실제 LLM 응답, 알림 표시)은 "검증"에 실행 명령과 기대 결과를 적고, 결과를 댓글로 남긴다.
- 진단 품질을 바꾸는 PR(턴 수, 진단 시간, 원인 적중)은 **전후 수치**를 남긴다. `diagnostics.csv`의 `ai_latency`, ReAct 턴 수를 근거로 쓴다.

### 작성 문체 (PR · Issue · 댓글 공통)

- **개조식**으로 쓴다. 서술형 문장(`~했다`, `~합니다`) 대신 명사형으로 끝낸다.
- 한 항목에 하나의 사실만 담는다. 근거(수치, 로그, 명령)를 함께 적는다.
- 추정과 확인을 구분한다: `~ 확인` / `~ 추정` / `~ 미확인`

| 서술형 (X) | 개조식 (O) |
|---|---|
| 응답 파싱이 실패했다 | 응답 파싱 실패 발생 |
| think 블록을 제거하도록 했습니다 | think 블록 제거 추가 |
| 원인은 모델 버전 차이로 보인다 | 원인: 모델 버전 차이 추정 |
| 테스트를 돌렸고 통과했다 | 테스트 수행, 통과 확인 |
| 알림이 오지 않았다 | 알림 미발생 |

자주 쓰는 종결어: 발생, 확인, 추정, 수행, 추가, 제거, 변경, 적용, 반영, 차단, 필요, 미확인, 해소

### 비밀값 규칙

- Discord 웹훅 URL, API 키는 **절대 커밋하지 않는다.** `.env`(git 제외) 또는 환경변수로만 넣는다.
- 새 비밀값이 필요하면 `.env.example`에 변수 이름과 빈 값(또는 자리표시자)만 추가한다.
- 로그 · 알림 · PR 본문에 비밀값이 찍히지 않게 한다.

### LLM이 실행하는 명령어 규칙

ReAct 루프는 LLM이 고른 명령어를 운영 서버에서 실행한다. 이 경로를 바꾸는 PR은 `security` 라벨을 붙이고 아래를 지킨다.

- 실행 가능한 명령은 **조회 전용**만 허용한다. 허용 목록을 넓히는 변경은 본문 "배경"에 이유를 적는다.
- 명령 검사를 바꾸면 **우회 시도 테스트**(명령 연결, 치환, 파일 쓰기 등)를 함께 추가한다.
- 검사 단계와 실행 단계가 같은 해석을 쓰게 한다. 검사는 통과했는데 셸이 다르게 해석하는 경로를 만들지 않는다.

## 4. 라벨

| 라벨 | 용도 |
|---|---|
| `bug` | 오동작 Issue |
| `enhancement` | 개선 Issue |
| `security` | 보안 관련 |
| `area:<scope>` | 위 scope 표와 동일 (`area:react` 등) |

## 5. AI와 함께 작업할 때

- AI는 브랜치 생성, 커밋, push, PR 생성까지 수행하고 **merge는 사람이 한다.**
- AI는 작업 전에 이 문서를 읽고, 이름과 본문 형식을 그대로 따른다.
- AI는 push 전에 `python -m pytest`를 실행하고 결과를 PR 본문 "검증"에 적는다.
- AI는 홈서버에 직접 접근하지 않는다. 서버 확인 명령은 AI가 제시하고 사람이 실행해 결과를 전달한다. 결과는 PR 댓글로 남긴다.
- AI가 확인하지 못한 가정(Ollama 버전, 모델 응답 형식 등)은 PR 본문 "Notes"에 명시한다.
- 여러 PR이 같은 파일을 건드리면 PR 본문 "Notes"에 merge 순서를 적는다. 앞 PR이 merge되면 AI가 뒤 PR을 최신 `main`으로 갱신한다.
